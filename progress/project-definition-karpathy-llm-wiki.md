# 项目定义：Karpathy LLM Wiki 在本项目中的落地边界

> 文件目的：明确本项目“是什么、不是什麽、当前阶段优先做什么”，避免后续开发跑偏。

## 1. 上游概念来源

本项目的思想来源于 Andrej Karpathy 在 **2026 年 4 月 4 日** 发布的 GitHub Gist《LLM Wiki》。

核心来源：
- Karpathy Gist 列表：<https://gist.github.com/karpathy>
- 原始 Gist《llm-wiki.md》：<https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f>

从该 Gist 可以提炼出几个核心观点：
1. 传统 RAG 在查询时临时从原始文档检索片段，知识不会真正“累积”。
2. LLM Wiki 的思路不是“每次都重新理解原始资料”，而是让 LLM 持续维护一份中间层 Wiki。
3. 这份 Wiki 是一个可持续更新、可交叉引用、可逐步复利的知识产物。
4. Raw sources 不应被修改；Wiki 层由 LLM 维护；Schema/规则文件约束 LLM 的行为。
5. Obsidian 更像 IDE，LLM 更像维护 Wiki 的程序员。

---

## 2. 本项目的目标是什么

本项目不是一个普通的“问答机器人”或“文章摘要器”。

本项目要做的是：

### 2.1 构建一个本地知识生产流水线
把外部资料持续转化为结构化、可维护、可查询、可治理的本地 Wiki。

### 2.2 构建一个“先编译、后查询”的知识系统
流程不是：
- 原始文档 -> 直接问答

而是：
- 原始文档 -> Ingest -> 结构化 Wiki -> Index -> Query / Lint

### 2.3 构建一个可复利的知识中间层
重点不在于“一次回答对不对”，而在于：
- 知识是否持续沉淀
- 结构是否持续变好
- 后续查询是否越来越稳定

### 2.4 构建一个可验收的流程系统
当前阶段最重要的不是“内容是否完美”，而是：
- APP 能否稳定输出指定结构
- 流程能否被规则约束
- 输出能否被 Index / Lint 验收

---

## 3. 本项目不是什么

为了避免跑偏，下面这些都不是当前阶段的核心目标：

### 3.1 不是通用聊天应用
不是围绕“聊天体验”设计的产品。

### 3.2 不是先做内容最优
当前阶段不优先追求：
- 文风最优
- 概念抽象最优
- 大模型语义判断最强

这些后续可以继续优化，但不是第一优先级。

### 3.3 不是先做复杂 RAG 基础设施
当前阶段不优先引入：
- 向量库
- 复杂检索编排
- 重型知识图谱引擎

当前应优先做可读、可维护、可落盘的 Markdown/Wiki 中间层。

### 3.4 不是以测试样本文本本身为中心
测试库中的具体文章内容是否“完全正确”，不是当前第一优先级。

当前更重要的是：
- 结构对不对
- 流程顺不顺
- 输出是否符合规则

## 4. 本项目当前应遵循的核心流程

### 4.1 Ingest
职责：
- 读取原始资料
- 生成结构化 Wiki 页面
- 输出 front matter、aliases、tags、entities
- 保证格式稳定、可持续维护

### 4.2 Index
职责：
- 全库扫描 Wiki
- 重建全局索引
- 生成 entities_map 路由表
- 暴露重复条目、孤立条目、标签分布

### 4.3 Query
职责：
- 优先通过 Index 路由问题
- 再读取命中文档
- 避免每次都盲扫原始资料或全库

### 4.4 Lint
职责：
- 检查知识库结构质量
- 暴露重复 ingest、相似标题、坏链、孤立 Note
- 为后续治理提供可操作摘要

---

## 5. 当前阶段的优先级（非常重要）

### 第一优先级：流程与输出结构稳定
包括：
- Ingest 输出结构稳定
- Index 能稳定重建
- Lint 能稳定发现结构问题
- 前端能稳定展示结果

### 第二优先级：规则治理
包括：
- 重复标题
- 高相似标题
- 坏链
- 孤立 Note
- 路由表完整性

### 第三优先级：内容语义增强
这部分后续再逐步加入：
- 更好的关键词抽取
- 更好的 aliases/entities 生成
- LLM 参与语义去重
- LLM 提供补链建议

---

## 6. LLM 在本项目中的定位

LLM 不是“全权裁判”，而是分阶段参与：

### 当前阶段
LLM 主要用于：
- Ingest 时编译知识

规则系统主要用于：
- Index 重建
- Lint 验收

### 后续阶段
LLM 才逐渐参与：
- 语义重复判断
- 概念归并建议
- 补链建议
- 结构质量建议

换句话说：
- 规则系统 = 基础设施
- LLM = 智能增强层

---

## 7. 当前阶段的验收标准

只要后续开发涉及 Ingest / Index / Query / Lint，都应优先问下面这些问题：

1. 输出结构是否稳定？
2. 结果是否可落盘？
3. 是否便于后续路由？
4. 是否便于后续治理？
5. 是否能通过 Lint 暴露问题？
6. 是否更接近“可持续维护的 Wiki”，而不是一次性回答？

如果某项改动只提升一次性回答效果，但削弱了结构稳定性或治理能力，则应谨慎。

---

## 8. 对本项目的一句工作定义

**这是一个把原始资料持续编译为本地结构化 Wiki，并围绕 Ingest / Index / Query / Lint 形成知识复利闭环的系统。**

当前阶段最重要的不是内容本身是否完美，而是：

**流程是否稳定、输出是否结构化、结果是否可路由、问题是否可验收。**
