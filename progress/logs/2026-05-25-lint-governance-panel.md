# 2026-05-25 Lint 治理面板增强记录

## 背景

今天继续围绕 Lint 做“结构治理”增强，而不是做 schema/frontmatter 校验。

用户确认的方向：

1. 当前更重要的是重复内容治理
2. `raw_file` 不能作为重复来源锚点
3. 应改为使用 `source_url` / 旧格式 `source`
4. Lint 结果不能只是平铺报错，还要更像治理面板，便于判断“是否符合要求”

此前已经完成：

- 基于 `source_url/source` 的 raw 层重复检测
- 基于 wiki → raw → source_url 的同源 wiki 重复检测

本次继续做两件事：

1. 优化评分逻辑，降低“提示类问题”对总分的噪音
2. 强化治理摘要，让用户更容易看懂当前该先处理什么

## 本次改动

### 1. 评分从“逐条重罚”改为“按治理桶分层扣分”

把问题分成 5 个治理桶：

- 重复 ingest / 同源重复编译
- 正文重复 / 标题高相似
- 路由与实体命中风险
- 坏链与孤立结构
- 占位文档 / 轻度结构提示

每个桶都有：

- 独立扣分逻辑
- 扣分上限
- 问题组数
- 治理信号数

这样可以避免：

- `broken_link_group`
- `orphan_note_group`

这类提示信息一多就直接把总分打到 0，导致分数失去解释力。

### 2. governance 增强为真正可读的“治理面板”

新增字段：

- `issueGroupCount`：治理信号总量
- `scoreBreakdown`：每个治理桶的扣分来源
- `sourceUrlHighlights`：
  - raw 层最严重的重复 source_url
  - wiki 层最严重的同源重复 source_url

这样用户看 Lint 时，不需要先翻完整问题列表，就能先看到：

- 哪一类问题最拖分
- 哪些 source_url 最值得先处理

### 3. 报告文件同步增强

输出到 `outputs/lint-report-*.md` 的报告现在也会包含：

- 治理面板摘要
- 评分拆解
- Source URL 重复重点
- 建议优先顺序

即使不看前端，也能直接从 markdown 报告判断本次 Lint 的治理价值。

### 4. 前端 Lint 页面补展示

`LintPage.jsx` 增加：

- 治理信号数
- 评分拆解卡片
- Source URL 重复重点卡片

目标不是重做 UI，而是在现有页面上把“该先治理什么”直接露出来。

## 这次改动的意义

当前阶段的项目重点不是追求“分数高”，而是：

1. 规则能否稳定跑通
2. 是否能暴露真实结构问题
3. 是否能指导治理动作

这次增强后，Lint 更接近一个治理验收面板，而不是单纯的报错列表。

## 下一步建议

如果这版效果确认可接受，下一步更值得做的是：

1. 给重复 source_url 组补“代表样本”输出
2. 给 broken_link / orphan_note 做降噪阈值
3. 加一个“仅看重复治理”视图或过滤入口
